# Migration 1.0.11 Checklist

The steps and commands to run Elasticsearch migration 1.0.11 in DEV, then TEST, then PROD. Background, settings and
troubleshooting are in the [runbook](./README.md).

Writers and services stay running throughout. Searches keep using the 1.0.10 indexes until the migration switches
the aliases at the end.

Checked on 2026-10-09:

| | DEV | TEST Cloud | PROD Cloud |
| ------------------------- | ---------------------------- | ------------------------------- | ------------------------------- |
| Migration history | 1.0.10 | empty | no `migrations` index |
| 1.0.10 fields in mappings | yes | yes | yes |
| `Story` content types | n/a | 0 | 0 |
| Baseline | none | `1.0.10` | `1.0.10` |
| Disk after the copy | ~88% per node on 50Gi volumes | ~82% of 60 GB, 1 data node | ~75%, fine |
| Snapshots | no snapshot repository | `found-snapshots`, daily | `found-snapshots`, daily |

The 1.0.10 `content` ingest pipeline is missing on both Cloud clusters. It only converted `Story` to `Internet` during
the 1.0.10 copy, and neither cluster has any `Story` documents, so the 1.0.10 baseline is still correct.

## 0. Set Up Your Shell

Run everything from the repository root, logged in with `oc login`.

```bash
# DEV: Elasticsearch through a pod
es() { oc exec -n 9b301c-dev elastic-0 -- curl -s "$@"; }

# TEST / PROD: Elastic Cloud through the indexing-service-cloud pod; pass a path only
escloud() { oc exec -n $N deploy/indexing-service-cloud -- sh -c "curl -s -H \"Authorization: ApiKey \$Elastic__ApiKey\" \"\$Elastic__Url/$1\""; }
```

## 1. Build the Migration Image

Once, before DEV. The image must include the change that removed `ELASTIC_MIGRATION_WRITERS_PAUSED`.

```bash
make -C openshift build n=elastic-migration t=latest
make -C openshift push n=elastic-migration t=latest
```

## 2. DEV

### 2.1 Check the Starting Point

```bash
es 'localhost:9200/_cat/health?v'                                   # green
es 'localhost:9200/_cat/aliases?v' | grep -v '^\.'                  # content -> content_v1.0.10, unpublished_content -> unpublished_content_v1.0.10
es 'localhost:9200/_cat/indices?v&s=index' | grep -v '^\.'          # no *_v1.0.11-* and no content_evidence
es 'localhost:9200/_tasks?actions=*reindex'                         # "nodes":{}
oc get jobs -n 9b301c-dev | grep elastic-migration                  # nothing running
oc get deploy indexing-service -n 9b301c-dev -o jsonpath='{.spec.replicas}{"\n"}'   # 0
```

If a `content_evidence` index exists, check it is empty and not an alias, then delete it:

```bash
es 'localhost:9200/_cat/indices/content_evidence?v&h=index,docs.count'
es 'localhost:9200/_alias/content_evidence'                         # expect 404 "alias missing"
es -XDELETE 'localhost:9200/content_evidence'
```

Keep `indexing-service` at 0 replicas until step 2.6, or it recreates `content_evidence` as a plain index.

### 2.2 Make Room on Disk

The copy needs about 21 GB more on each node, which would take the 50Gi volumes to about 88%. The storage class
(`netapp-block-standard`) allows expansion and the namespace storage quota has room for 80Gi volumes.

```bash
for i in 0 1 2; do
  oc patch pvc data-elastic-$i -n 9b301c-dev -p '{"spec":{"resources":{"requests":{"storage":"80Gi"}}}}'
done
oc get pvc -n 9b301c-dev | grep elastic                              # CAPACITY 80Gi
es 'localhost:9200/_cat/allocation?v'                               # disk.total about 80gb per node
```

If a volume shows `FileSystemResizePending`, restart its pod using
[Restart the Pods One at a Time](./README.md#restart-the-pods-one-at-a-time) so the filesystem grows.

### 2.3 Run the Migration

```bash
make -C openshift deploy n=elastic-migration e=dev t=latest m=1.0.11
```

`deploy` follows the Job's logs. If your terminal disconnects, the Job keeps running.

### 2.4 Watch Progress

Note how long the copy takes; it is the best guide for TEST and PROD.

```bash
oc get jobs -n 9b301c-dev | grep elastic-migration
oc logs -f job/<job-name> -n 9b301c-dev
es 'localhost:9200/_tasks?actions=*reindex&detailed=true' | grep -o '"total":[0-9]*\|"created":[0-9]*'
es 'localhost:9200/_cat/allocation?v'
```

To stop the run, follow [Stop a Running Migration](./README.md#stop-a-running-migration) in that order. Do not cancel
the Elasticsearch task while the Job is still running.

### 2.5 Check the Result

```bash
es 'localhost:9200/_cat/aliases?v' | grep -v '^\.'          # content, unpublished_content, content_evidence -> *_v1.0.11-<generation>
es 'localhost:9200/migrations/_doc/1.0.11?filter_path=_source'
es 'localhost:9200/_cat/health?v'
```

Then in DEV:

- [ ] Editor search returns content.
- [ ] Subscriber search returns published content; unapproved audio/video transcripts are not shown.
- [ ] A report using AI evidence runs.

### 2.6 Turn Indexing Back On

```bash
oc scale deployment indexing-service -n 9b301c-dev --replicas=1
oc logs -f deploy/indexing-service -n 9b301c-dev            # "Subscribing to topics: index", then content indexed
```

Keep the `_v1.0.10` indexes until you are satisfied; delete them later by exact name.

## 3. TEST

```bash
N=9b301c-test
```

### 3.1 Check the Starting Point

```bash
escloud '_cat/health?v'
escloud '_cat/aliases?v'                                    # content -> content_v1.0.10, published_content -> published_content_v1.0.10
escloud '_cat/indices?v&s=index'                            # no *_v1.0.11-* and no content_evidence
escloud '_cat/allocation?v'
escloud '_tasks?actions=*reindex'                           # "nodes":{}
escloud '_cat/snapshots/found-snapshots?v&s=end_epoch:desc' | head -3   # a recent SUCCESS snapshot
```

### 3.2 Make Room on Disk

The copy needs about 25 GB, taking the single 60 GB data node to about 82%. Increase the TEST deployment's storage in
the Elastic Cloud console first, so it stays well under 85% after the copy.

### 3.3 Run the Migration

```bash
ELASTIC_MIGRATION_BASELINE=1.0.10 make -C openshift deploy n=elastic-migration e=test t=latest m=1.0.11
```

The baseline stops older migrations running. Because `migrations` is empty, the tool first records every migration up
to 1.0.10 as `baseline` without running them, then runs only 1.0.11. Without the baseline it stops before changing
anything.

Watch it as in 2.4 using `escloud` and `9b301c-test`. Record how long the copy takes:
PROD has about 2.3 times as many documents.

### 3.4 Check the Result

```bash
escloud '_cat/aliases?v'                                    # content, published_content, content_evidence -> *_v1.0.11-<generation>
escloud 'migrations/_search?size=50&filter_path=hits.hits._id,hits.hits._source.description'   # 1.0.0 to 1.0.10 "baseline", then 1.0.11
escloud '_cat/health?v'
```

- [ ] Editor search, subscriber search and an AI report work in TEST.

## 4. PROD

```bash
N=9b301c-prod
```

### 4.1 Check the Starting Point

Same checks as 3.1 with `N=9b301c-prod`. PROD has enough disk.

### 4.2 Run the Migration

Use a 48-hour Job limit unless TEST finished well inside 10 hours.

```bash
ELASTIC_MIGRATION_BASELINE=1.0.10 MIGRATION_ACTIVE_DEADLINE_SECONDS=172800 \
  make -C openshift deploy n=elastic-migration e=prod t=latest m=1.0.11
```

### 4.3 Check the Result

Same checks as 3.4 with `N=9b301c-prod`.

- [ ] Editor search, subscriber search and an AI report work in PROD.

## 5. Afterwards

- Keep the `_v1.0.10` indexes in each environment until the checks above and the retention window pass, then delete
  them by exact name.
- Commit the Elasticsearch StatefulSet changes in `openshift/kustomize/elastic` so the next kustomize apply does not
  undo the DEV resources, heap and probe.

# Migration 1.0.11 Checklist

The steps and commands to run Elasticsearch migration 1.0.11 in DEV, then TEST, then PROD, without downtime. Background,
settings and troubleshooting are in the [runbook](./README.md).

Each environment runs the migration as four Jobs: `prepare`, `copy`, `verify`, `cutover`. The live indexing service
keeps writing to the live indexes the whole time. Between `prepare` and the end of `cutover`, a temporary
[second indexing service](./README.md#second-indexing-service) writes the same changes into the new indexes. Search
stays current throughout and moves to the new indexes when `cutover` switches the aliases.

| Environment | Live indexing service (copied for the second one) | Normal replicas |
| ----------- | ------------------------------------------------- | --------------- |
| DEV | `indexing-service` | 1 |
| TEST | `indexing-service-cloud` | 2 |
| PROD | `indexing-service-cloud` | 3 |

In TEST and PROD, `indexing-service` writes to the local OpenShift Elasticsearch, which is not migrated, and sends
alerts. Leave it alone.

Checked on 2026-10-09:

| | DEV | TEST Cloud | PROD Cloud |
| ------------------------- | ---------------------------- | ------------------------------- | ------------------------------- |
| Migration history | 1.0.10 | empty | no `migrations` index |
| 1.0.10 fields in mappings | yes | yes | yes |
| `Story` content types | n/a | 0 | 0 |
| Baseline | none | `1.0.10` | `1.0.10` |
| Disk after cutover | ~88% per node on 50Gi volumes | ~82% of 60 GB, 1 data node | ~75%, fine |
| Snapshots | no snapshot repository | `found-snapshots`, daily | `found-snapshots`, daily |

The 1.0.10 `content` ingest pipeline is missing on both Cloud clusters. It only converted `Story` to `Internet` during
the 1.0.10 copy, and neither cluster has any `Story` documents, so the 1.0.10 baseline is still correct.

## 0. Set Up Your Shell

Run everything from the repository root, logged in with `oc login`.

```bash
# DEV: Elasticsearch through a pod
es() { oc exec -n 9b301c-dev elastic-0 -- curl -s "$@"; }

# TEST / PROD: Elastic Cloud directly from your machine; run cloudlogin after setting N, then pass a path only
cloudlogin() {
  ESKEY=$(oc get secret elastic-cloud -n $N -o jsonpath='{.data.ApiKey}' | base64 -d)
  ESURL=$(oc get configmap indexing-service-cloud -n $N -o jsonpath='{.data.ELASTICSEARCH_URI}')
}
escloud() { curl -s -H "Authorization: ApiKey $ESKEY" "$ESURL/$1"; }

# Kafka backlog of an indexing consumer group: LAG per partition
lag() { oc exec -n $N kafka-broker-0 -- kafka-consumer-groups --bootstrap-server kafka-headless:29092 --describe --group $1; }

# Run one step of the migration
step() { make -C openshift deploy n=elastic-migration e=$E t=latest m=1.0.11 p=$1; }
```

## 1. Build the Migration Image

Once, before DEV. The image must include the migration steps (`p=`).

```bash
make -C openshift build n=elastic-migration t=latest
make -C openshift push n=elastic-migration t=latest
```

## 2. DEV

```bash
N=9b301c-dev; E=dev; SRC=indexing-service
```

### 2.1 Check the Starting Point

```bash
es 'localhost:9200/_cat/health?v'                                   # green
es 'localhost:9200/_cat/aliases?v' | grep -v '^\.'                  # content -> content_v1.0.10, unpublished_content -> unpublished_content_v1.0.10
es 'localhost:9200/_cat/indices?v&s=index' | grep -v '^\.'          # no *_v1.0.11-*
es 'localhost:9200/_tasks?actions=*reindex'                         # "nodes":{}
oc get jobs -n $N | grep elastic-migration                          # nothing running
oc get deploy -n $N | grep indexing-service                         # indexing-service 1/1, no indexing-service-migration
```

A concrete `content_evidence` index may exist; the running indexing service recreates it. Cutover backs it up and
replaces it with the alias, so leave it.

### 2.2 Make Room on Disk

Cutover adds about 21 GB on each node, which would take the 50Gi volumes to about 88%. The storage class
(`netapp-block-standard`) allows expansion and the namespace storage quota has room for 80Gi volumes.

```bash
for i in 0 1 2; do
  oc patch pvc data-elastic-$i -n $N -p '{"spec":{"resources":{"requests":{"storage":"80Gi"}}}}'
done
oc get pvc -n $N | grep elastic                                     # CAPACITY 80Gi
es 'localhost:9200/_cat/allocation?v'                               # disk.total about 80gb per node
```

If a volume shows `FileSystemResizePending`, restart its pod using
[Restart the Pods One at a Time](./README.md#restart-the-pods-one-at-a-time) so the filesystem grows.

### 2.3 Prepare

```bash
step prepare
```

The end of the log names the new indexes:

```text
CONTENT_INDEX (Elastic__ContentIndex)=unpublished_content_v1.0.11-<generation>
PUBLISHED_INDEX (Elastic__PublishedIndex)=content_v1.0.11-<generation>
EVIDENCE_INDEX (Elastic__EvidenceIndex)=content_evidence_v1.0.11-<generation>
```

```bash
es 'localhost:9200/_cat/indices/*_v1.0.11-*?v'                      # three new indexes, 0 docs
```

### 2.4 Start the Second Indexing Service

Create `indexing-service-migration` from `$SRC` with the three index names from 2.3, following
[Second Indexing Service](./README.md#second-indexing-service). Then check it writes to the new indexes:

```bash
oc logs -f deploy/indexing-service-migration -n $N                  # "Subscribing to topics: index", then "Content indexed ... Index: unpublished_content_v1.0.11-..."
lag IndexingMigration                                               # LAG near 0
```

Keep it running until 2.7 has finished.

### 2.5 Copy

```bash
step copy
```

`deploy` follows the Job's logs. If your terminal disconnects, the Job keeps running. Note how long the copy takes;
it is the best guide for TEST and PROD.

```bash
oc get jobs -n $N -l component=elastic-migration
es 'localhost:9200/_tasks?actions=*reindex&detailed=true' | grep -o '"total":[0-9]*\|"created":[0-9]*'
es 'localhost:9200/_cat/allocation?v'
```

To stop it, follow [Stop a Running Migration](./README.md#stop-a-running-migration).

### 2.6 Verify

```bash
step verify
```

The log ends with `Verified '<index>'` for each of the three indexes.

### 2.7 Cutover

```bash
step cutover
```

It restores the replicas and waits for them, moves the aliases, then verifies again.

```bash
es 'localhost:9200/_cat/aliases?v' | grep -v '^\.'                  # content, unpublished_content, content_evidence -> *_v1.0.11-<generation>
es 'localhost:9200/migrations/_doc/1.0.11?filter_path=_source'
es 'localhost:9200/_cat/health?v'                                   # green
```

### 2.8 Remove the Second Indexing Service

Only once 2.7 has succeeded.

```bash
oc delete deploy/indexing-service-migration -n $N
```

### 2.9 Test the Application

- [ ] Editor search returns content, including content changed during the migration.
- [ ] Subscriber search returns published content; unapproved audio/video transcripts are not shown.
- [ ] A report using AI evidence runs.

Keep the `_v1.0.10` indexes until you are satisfied; delete them later by exact name.

## 3. TEST

```bash
N=9b301c-test; E=test; SRC=indexing-service-cloud
export ELASTIC_MIGRATION_BASELINE=1.0.10
cloudlogin
```

The baseline stops older migrations running. `migrations` is empty, so the first step records every migration up to
1.0.10 as `baseline` without running them; after that the baseline is ignored. Without it, the step stops before
changing anything.

### 3.1 Check the Starting Point

```bash
escloud '_cat/health?v'
escloud '_cat/aliases?v'                                    # content -> content_v1.0.10, published_content -> published_content_v1.0.10
escloud '_cat/indices?v&s=index'                            # no *_v1.0.11-*
escloud '_cat/allocation?v'
escloud '_tasks?actions=*reindex'                           # "nodes":{}
escloud '_cat/snapshots/found-snapshots?v&s=end_epoch:desc' | head -3   # a recent SUCCESS snapshot
```

### 3.2 Make Room on Disk

Cutover takes the single 60 GB data node to about 82%. Increase the TEST deployment's storage in the Elastic Cloud
console first, so it stays well under 85%.

### 3.3 Run the Steps

As DEV 2.3 to 2.8, using `escloud '<path>'` in place of `es 'localhost:9200/<path>'`:

1. `step prepare`, and note the three index names.
2. Create `indexing-service-migration` from `indexing-service-cloud` with those names, and check its log and
   `lag IndexingMigration`.
3. `step copy`. Record how long it takes: PROD has about 2.3 times as many documents.
4. `step verify`.
5. `step cutover`, then check:

   ```bash
   escloud '_cat/aliases?v'                                 # content, published_content, content_evidence -> *_v1.0.11-<generation>
   escloud 'migrations/_search?size=50&filter_path=hits.hits._id,hits.hits._source.description'   # 1.0.0 to 1.0.10 "baseline", then 1.0.11
   escloud '_cat/health?v'
   ```

6. `oc delete deploy/indexing-service-migration -n $N`

- [ ] Editor search, subscriber search and an AI report work in TEST.

## 4. PROD

```bash
N=9b301c-prod; E=prod; SRC=indexing-service-cloud
export ELASTIC_MIGRATION_BASELINE=1.0.10
cloudlogin
```

As TEST 3.1 and 3.3. PROD has enough disk. Give the copy a 48-hour Job limit unless TEST's copy finished well inside
10 hours:

```bash
MIGRATION_ACTIVE_DEADLINE_SECONDS=172800 step copy
```

- [ ] Editor search, subscriber search and an AI report work in PROD.

## 5. Afterwards

- If a step fails or is stopped before cutover, the aliases have not moved and the live indexing service has kept
  search current. Leave the second indexing service running, follow
  [If the Job Fails or Times Out](./README.md#if-the-job-fails-or-times-out), then rerun that step.
- Keep the `_v1.0.10` indexes in each environment until the checks above and the retention window pass, then delete
  them by exact name.

# Migration 1.0.11 Checklist

The steps and commands to run Elasticsearch migration 1.0.11 in DEV, then TEST, then PROD, without downtime. Background,
settings and troubleshooting are in the [runbook](./README.md).

Each environment runs the migration as four Jobs: `prepare`, `copy`, `verify`, `cutover`. They start with a short
**indexing pause**: every indexing service is scaled to 0 while the other services are updated. Only three things
must happen inside the pause, because they decide where the new indexes start reading Kafka:

1. `step prepare` creates the new indexes and prints their names.
2. A temporary [second indexing service](./README.md#second-indexing-service), `indexing-service-migration`, is
   created for the new indexes, with no pods.
3. Its Kafka consumer group, `IndexingMigration`, is set to the exact positions where the live indexer stopped.

Then the live indexer and the second indexing service start together and work through the backlog that built up during
the pause. Each writes every content change to its own indexes from the same message onwards, so the new indexes miss
nothing. `copy`, `verify` and `cutover` run afterwards with indexing on, for as long as they take. Search stays on the
live indexes until `cutover` switches the aliases.

| Environment | Live indexing service | Its consumer group (`$G`) |
| ----------- | --------------------- | ------------------------- |
| DEV | `indexing-service` | `Indexing` |
| TEST | `indexing-service-cloud` | `IndexingCloud` |
| PROD | `indexing-service-cloud` | `IndexingCloud` |

In TEST and PROD, the pause also retires the local OpenShift Elasticsearch and its `indexing-service` (consumer
group `Indexing`), and turns `INDEX_ONLY` off on `indexing-service-cloud`. See [3.1](#31-pause-indexing-and-retire-the-local-cluster).

Checked on 2026-10-09:

| | DEV | TEST Cloud | PROD Cloud |
| ------------------------- | ---------------------------- | ------------------------------- | ------------------------------- |
| Migration history | 1.0.10 | empty | no `migrations` index |
| 1.0.10 fields in mappings | yes | yes | yes |
| `Story` content types | n/a | 0 | 0 |
| Baseline | none | `1.0.10` | `1.0.10` |
| Disk after cutover | ~79% per node on 55Gi volumes | ~82% of 60 GB, 1 data node | ~75%, fine |
| Snapshots | no snapshot repository | `found-snapshots`, daily | `found-snapshots`, daily |

The 1.0.10 `content` ingest pipeline is missing on both Cloud clusters. It only converted `Story` to `Internet` during
the 1.0.10 copy, and neither cluster has any `Story` documents, so the 1.0.10 baseline is still correct.

## 0. Set Up Your Shell

Run everything from the repository root, logged in with `oc login`. Paste this block into **every** terminal you use
(for example a second one to watch a Job), then run `useenv` for the environment you are working on. `useenv` sets
every variable the commands below rely on, and prints them.

```bash
# Set the variables for one environment: useenv dev | test | prod
useenv() {
  case "$1" in dev|test|prod) ;; *) echo "usage: useenv dev|test|prod"; return 1 ;; esac
  E=$1                                                        # make deploy e=
  N=9b301c-$E                                                 # OpenShift namespace
  O=openshift/kustomize/services/indexing/overlays/migration-$E   # second indexing service overlay
  unset ELASTIC_MIGRATION_BASELINE MIGRATION_ACTIVE_DEADLINE_SECONDS ESKEY ESURL
  if [[ $E == dev ]]; then
    D=indexing-service                                        # live indexing Deployment
    G=Indexing                                                # its consumer group
  else
    D=indexing-service-cloud
    G=IndexingCloud
    export ELASTIC_MIGRATION_BASELINE=1.0.10                  # Cloud has no migration history; ignored once it does
    ESKEY=$(oc get secret elastic-cloud -n $N -o jsonpath='{.data.ApiKey}' | base64 -d)
    ESURL=$(oc get configmap indexing-service-cloud -n $N -o jsonpath='{.data.ELASTICSEARCH_URI}')
  fi
  echo "E=$E N=$N D=$D G=$G O=$O ELASTIC_MIGRATION_BASELINE=${ELASTIC_MIGRATION_BASELINE:-} ESURL=${ESURL:-}"
}

# DEV Elasticsearch through a pod: es 'localhost:9200/<path>'
es() { oc exec -n 9b301c-dev elastic-0 -- curl -s "$@"; }

# TEST / PROD Elastic Cloud directly from your machine: escloud '<path>'
escloud() { curl -s -H "Authorization: ApiKey $ESKEY" "$ESURL/$1"; }

# Kafka position and backlog of a consumer group: CURRENT-OFFSET and LAG per partition.
# In DEV every broker advertises the same address, so finding a group's coordinator can take several tries: hence --timeout.
lag() { oc exec -n $N kafka-broker-0 -- kafka-consumer-groups --bootstrap-server kafka-headless:29092 --timeout 60000 --describe --group $1; }

# Copy a stopped consumer group's 'index' positions to another stopped group: syncgroup <from> <to> [--execute]
# Without --execute it only prints the new positions. It refuses if <from> is running or has no positions.
syncgroup() {
  oc exec -i -n $N kafka-broker-0 -- bash -s -- "$1" "$2" "${3:---dry-run}" <<'SH'
K="kafka-consumer-groups --bootstrap-server kafka-headless:29092 --timeout 60000"
D=$($K --describe --group "$1" 2>&1)
grep -q "has no active members" <<<"$D" || { echo "ERROR: $1 is running or missing; stop it first."; echo "$D" | head -4; exit 1; }
F=$(mktemp)
awk '$2=="index" && $4 ~ /^[0-9]+$/ {print $2","$3","$4}' <<<"$D" > "$F"
[ -s "$F" ] || { echo "ERROR: $1 has no committed offsets on 'index'."; rm -f "$F"; exit 1; }
$K --group "$2" --reset-offsets --from-file "$F" "$3"
rm -f "$F"
SH
}

# Run one step of the migration
step() { make -C openshift deploy n=elastic-migration e=$E t=latest m=1.0.11 p=$1; }
```

## 1. Build the Migration Image

Once, before DEV, from a checkout that includes the migration steps (`p=`). An older image ignores the step and runs
the whole migration in one Job.

```bash
make -C openshift build n=elastic-migration t=latest
make -C openshift push n=elastic-migration t=latest
```

## 2. DEV

```bash
useenv dev
```

### 2.1 Check the Starting Point

```bash
es 'localhost:9200/_cat/health?v'                                   # green
es 'localhost:9200/_cat/aliases?v' | grep -v '^\.'                  # content -> content_v1.0.10, unpublished_content -> unpublished_content_v1.0.10
es 'localhost:9200/_cat/indices?v&s=index' | grep -v '^\.'          # no *_v1.0.11-*
es 'localhost:9200/_tasks?actions=*reindex'                         # "nodes":{}
oc get jobs -n $N | grep elastic-migration                          # nothing running
oc get deploy -n $N | grep indexing-service                         # note indexing-service's READY count (normally 1); no indexing-service-migration
```

A concrete `content_evidence` index may exist; the running indexing service recreates it. Cutover backs it up and
replaces it with the alias, so leave it.

### 2.2 Make Room on Disk

Each node holds about 22 GB on a 55Gi volume (40%). Cutover adds about 21 GB on each node, taking it to about 79%,
close to the 85% low watermark once merges and new writes are counted. The storage class (`netapp-block-standard`)
allows expansion and the namespace storage quota has room for 80Gi volumes.

```bash
for i in 0 1 2; do
  oc patch pvc data-elastic-$i -n $N -p '{"spec":{"resources":{"requests":{"storage":"80Gi"}}}}'
done
oc get pvc -n $N | grep elastic                                     # CAPACITY 80Gi
es 'localhost:9200/_cat/allocation?v'                               # disk.total about 80gb per node
```

If a volume shows `FileSystemResizePending`, restart its pod using
[Restart the Pods One at a Time](./README.md#restart-the-pods-one-at-a-time) so the filesystem grows.

### 2.3 Pause Indexing

```bash
oc scale deploy/$D -n $N --replicas=0
oc get deploy $D -n $N                                              # 0/0
lag $G                                                              # "Consumer group 'Indexing' has no active members."
```

Update the other services now if you are. Run 2.4 to 2.6 before indexing starts again.

### 2.4 Prepare

```bash
step prepare
```

The log must start with `Applying migration 1.0.11, step 'prepare'`. If it says only `Applying migration 1.0.11`,
the image predates the steps and is running the whole migration: stop it
([Stop a Running Migration](./README.md#stop-a-running-migration)) and rebuild the image (section 1).

The end of the log names the new indexes:

```text
CONTENT_INDEX (Elastic__ContentIndex)=unpublished_content_v1.0.11-<generation>
PUBLISHED_INDEX (Elastic__PublishedIndex)=content_v1.0.11-<generation>
EVIDENCE_INDEX (Elastic__EvidenceIndex)=content_evidence_v1.0.11-<generation>
```

```bash
es 'localhost:9200/_cat/indices/*_v1.0.11-*?v'                      # three new indexes, 0 docs
```

### 2.5 Create the Second Indexing Service

Create `indexing-service-migration` from the `migration-dev` overlay with the three index names from 2.4 (see
[Second Indexing Service](./README.md#second-indexing-service)). It is created with no pods. It runs the environment's
current `indexing-service` image. Until that image includes the `IndexOnly` fix from #2667, the second service also
forwards every message to the `folder` topic, so `folder-collection-service` handles each one twice.

```bash
oc apply -k $O
oc patch configmap indexing-service-migration -n $N --type merge -p '{"data":{
  "CONTENT_INDEX":"<CONTENT_INDEX>","PUBLISHED_INDEX":"<PUBLISHED_INDEX>","EVIDENCE_INDEX":"<EVIDENCE_INDEX>"}}'
oc get configmap indexing-service-migration -n $N -o jsonpath='{.data}{"\n"}'   # the three names, INDEX_ONLY "true"
```

### 2.6 Start It Where the Live Indexer Stopped

Copy the live group's positions on the `index` topic to `IndexingMigration`, so the second service starts at the same
message as the live one. Both groups must be stopped, which they are during the pause. An `IndexingMigration` group
left from an earlier attempt is overwritten.

```bash
syncgroup $G IndexingMigration                                      # dry run: one line per partition
lag $G                                                              # the same CURRENT-OFFSET values
syncgroup $G IndexingMigration --execute
lag IndexingMigration                                               # CURRENT-OFFSET matches lag $G
```

### 2.7 Resume Indexing

Start both together. Scale the live indexer back to the count from 2.1.

```bash
oc scale deploy/$D -n $N --replicas=1
oc scale deploy/indexing-service-migration -n $N --replicas=1
oc logs -f deploy/indexing-service-migration -n $N                  # "Subscribing to topics: index", then "Content indexed ... Index: unpublished_content_v1.0.11-..."
lag $G; lag IndexingMigration                                       # LAG falls to near 0 on both
```

The pause is over. Keep the second indexing service running until 2.10 has finished.

If indexing has to start again before 2.6 is done, start only the live indexer. Finish 2.5, start the second service
without 2.6 (it then starts at the newest message), and run `step copy` only once `lag $G` is near 0. `verify` repairs
anything the copy and the second service missed.

### 2.8 Copy

```bash
step copy
```

`deploy` follows the Job's logs. If your terminal disconnects, the Job keeps running. Note how long the copy takes;
it is the best guide for TEST and PROD.

```bash
oc get jobs -n $N -l component=elastic-migration
es 'localhost:9200/_tasks?actions=*reindex&detailed=true' | grep -o '"total":[0-9]*\|"created":[0-9]*'
es 'localhost:9200/_cat/allocation?v'
```

To stop it, follow [Stop a Running Migration](./README.md#stop-a-running-migration).

### 2.9 Verify

```bash
step verify
```

The log ends with `Verified '<index>'` for each of the three indexes.

### 2.10 Cutover

```bash
step cutover
```

It restores the replicas and waits for them, moves the aliases, then verifies again.

```bash
es 'localhost:9200/_cat/aliases?v' | grep -v '^\.'                  # content, unpublished_content, content_evidence -> *_v1.0.11-<generation>
es 'localhost:9200/migrations/_doc/1.0.11?filter_path=_source'
es 'localhost:9200/_cat/health?v'                                   # green
```

### 2.11 Remove the Second Indexing Service

Only once 2.10 has succeeded.

```bash
oc delete -k $O
```

### 2.12 Test the Application

- [ ] Editor search returns content, including content changed during the pause and the migration.
- [ ] Subscriber search returns published content; unapproved audio/video transcripts are not shown.
- [ ] A report using AI evidence runs.

Keep the `_v1.0.10` indexes until you are satisfied; delete them later by exact name.

## 3. TEST

```bash
useenv test
```

`useenv` sets `ELASTIC_MIGRATION_BASELINE=1.0.10` for TEST and PROD. The baseline stops older migrations running.
`migrations` is empty, so the first step records every migration up to 1.0.10 as `baseline` without running them;

### 3.0 Before the Pause

```bash
escloud '_cat/health?v'
escloud '_cat/aliases?v'                                    # content -> content_v1.0.10, published_content -> published_content_v1.0.10
escloud '_cat/indices?v&s=index'                            # no *_v1.0.11-*

escloud '_cat/snapshots/found-snapshots?v&s=end_epoch:desc' | head -3   # a recent SUCCESS snapshot

oc get configmap indexing-service-cloud -n $N -o jsonpath='{.data.INDEX_ONLY}{"\n"}'   # true until 3.1
```

Cutover takes the single 60 GB data node to about 82%. Increase the TEST deployment's storage in the Elastic Cloud
console first, so it stays well under 85%.

### 3.1 Pause Indexing and Retire the Local Cluster

Today the local `indexing-service` (`INDEX_ONLY=false`, group `Indexing`) moves content from Publish to Published and
sends alerts, notifications and `folder` messages, while `indexing-service-cloud` (`INDEX_ONLY=true`, group
`IndexingCloud`) only indexes. During the pause the cloud one takes those duties over, from the exact message where the
local one stopped, so nothing is sent twice or skipped. The repo's cloud overlays already set `INDEX_ONLY=false`
([components/cloud](../services/indexing/components/cloud)).

1. **Stop the local indexing service first**, so the cloud one moves past it.

   ```bash
   oc scale deploy/indexing-service -n $N --replicas=0
   lag Indexing                                             # has no active members
   lag IndexingCloud                                        # on every partition, CURRENT-OFFSET at or past Indexing's
   ```

   Wait until every partition of `IndexingCloud` is at or past `Indexing`. Otherwise step 4 would move the cloud
   indexer past messages it has not yet indexed.

2. **Stop the cloud indexing service.** Indexing is now paused.

   ```bash
   oc scale deploy/indexing-service-cloud -n $N --replicas=0
   lag IndexingCloud                                        # has no active members
   ```

3. **Point every reader at Cloud.** `folder-collection-service` and `notification-service` still read
   `ELASTICSEARCH_URI` from the `indexing-service` ConfigMap (`http://elastic:9200`). Their TEST overlays already use
   `indexing-service-cloud`; check the diff, then apply them.

   ```bash
   for s in folder-collection notification; do oc diff -k openshift/kustomize/services/$s/overlays/test; done
   for s in folder-collection notification; do oc apply -k openshift/kustomize/services/$s/overlays/test; done
   for d in folder-collection-service notification-service; do
     oc get deploy $d -n $N -o json | jq -r '[.spec.template.spec.containers[0].env[] | select(.name|startswith("Elastic__")) | .name + " <- " + (.valueFrom.configMapKeyRef.name // .valueFrom.secretKeyRef.name)] | .[]'
   done                                                     # every line: indexing-service-cloud or elastic-cloud
   ```

4. **Hand the local position to the cloud indexer and turn INDEX_ONLY off.** From the local position onwards it
   sends the status updates, alerts and `folder` messages the local one had not sent yet, and re-indexes what it had
   already indexed; the revision check makes that harmless.

   ```bash
   syncgroup Indexing IndexingCloud                         # dry run
   syncgroup Indexing IndexingCloud --execute
   lag IndexingCloud                                        # CURRENT-OFFSET now matches lag Indexing
   oc patch configmap indexing-service-cloud -n $N --type merge -p '{"data":{"INDEX_ONLY":"false"}}'
   oc get configmap indexing-service-cloud -n $N -o jsonpath='{.data.INDEX_ONLY}{"\n"}'   # false
   ```

   No restart is needed: its pods read the new value when they start in 3.5. Applying the `cloud-test` overlay gives
   the same value, but also brings in the rest of the ConfigMap and Deployment that have changed since it was last
   applied; `oc diff -k` it first if you do.

5. **Scale the local Elasticsearch down.** Its volumes are kept.

   ```bash
   oc scale statefulset elastic -n $N --replicas=0
   ```

`make up` keeps the local `indexing-service` at 0 and `indexing-service-cloud` at 2 (TEST) or 3 (PROD).

### 3.2 Prepare

`step prepare`, and check its log and the three index names as DEV 2.4, using `escloud '<path>'` in place of

### 3.3 Create the Second Indexing Service

As DEV 2.5: `oc apply -k $O`, then patch the three index names. It writes to TEST Elastic Cloud.

### 3.4 Start It Where the Live Indexer Stopped

```bash

oc logs -f deploy/indexing-service-migration -n $N          # "Content indexed ... Index: unpublished_content_v1.0.11-..."

```

## 5. Afterwards

- If a step fails or is stopped before cutover, the aliases have not moved and the live indexing service has kept
  search current. Leave the second indexing service running, follow
  [If the Job Fails or Times Out](./README.md#if-the-job-fails-or-times-out), then rerun that step.
- Keep the `_v1.0.10` indexes in each environment until the checks above and the retention window pass, then delete
  them by exact name.
